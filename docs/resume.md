# 作品集表述建议

## 项目名称

**知衡｜企业知识与流程 Agent（RAG + 受控业务执行）**

## 一句话介绍

面向模拟电商售后场景，独立完成从文档检索、引用核验到订单查询、人工审批、幂等工单、任务恢复与固定集评测的全栈 AI 应用。

## 简历项目描述

- 使用 **FastAPI + React + TypeScript** 构建企业知识与流程 Agent，打通文档管理、可追溯问答、订单工具、工单审批、报告生成与审计的完整业务闭环。
- 实现本地哈希向量与关键词混合检索，为回答保存文档版本、切片原文、定位与相关分数；对低相关问题执行无依据拒答，支持用户反馈与引用核验。
- 采用**显式业务状态流 + 人工审批**控制 Agent 副作用，结合 Pydantic Schema、参数白名单、业务规则与幂等键，确保工单未经审批不执行、重复提交不重复创建。
- 建立文档异步索引与失败恢复机制，使用 Redis/RQ、SSE 和任务状态记录支持处理进度、错误诊断与安全重试。
- 设计版本化固定评测集，保存逐用例回答、引用、工具结果、延迟与 Token，提供通过率、异常用例和工具调用审计视图。
- 提供 SQLite 本地开发模式与 **PostgreSQL/pgvector + Redis + Docker Compose** 部署模式，默认离线可运行，在线模型通过适配器可选接入并支持失败降级。

## 面试讲解主线

### 1. 为什么不只做 RAG 聊天？

普通上传文档问答很难证明业务价值，也无法证明系统能安全执行。这个项目把重点放在“证据是否可核验、工具参数是否合法、写入是否经过审批、失败后能否恢复、质量是否可重复测量”。

### 2. Agent 自主性在哪里？

用户自然语言先进入确定性业务分流：订单号触发只读工具，售后办理生成工单草案，其他问题进入检索问答。模型可辅助生成内容，但不能任意选择系统能力或直接执行写操作。

### 3. 如何防止重复工单？

每个草案拥有独立幂等键，审批通过时先检查该键对应的工单是否已存在。已批准记录的重复批准返回既有结果，不再次创建。

### 4. 为什么采用本地哈希向量？

演示环境需要零密钥、低成本、可复现。它适合验证检索、引用和工程闭环，但不等于神经语义嵌入。检索接口与存储边界已隔离，后续可替换为真实嵌入模型与 pgvector 查询。

### 5. 如何评价系统质量？

不用主观“看起来回答不错”，而是用固定 JSON 用例验证必含内容、引用存在性、无依据拒答和订单状态；每次保存数据版本、应用版本、延迟、Token 和错误记录。

## 可展示的技术亮点

1. **引用不是装饰**：抽屉直接显示当前有效版本的原文和定位。
2. **写操作有边界**：页面没有直接创建工单入口，后端也不存在绕过审批的创建接口。
3. **审批不是单个确认框**：支持修改参数、拒绝原因、执行结果和报告。
4. **失败是一等状态**：文档阶段、错误、重试次数与任务入口均可查看。
5. **质量可回归**：固定集结果可重复运行并保留历史，而非只做一次演示。

## 下一步增强（与当前已完成范围区分）

- 使用真实神经嵌入、pgvector 数据库检索与独立重排模型。
- 增加文档级权限、用户身份与多租户隔离。
- 接入真实订单 / 工单系统的只读沙箱，并补充超时后的结果查询。
- 扩展扫描 PDF OCR、表格结构解析与文档版本 diff。
- 建立更大人工金标集和按问题类型拆分的质量指标。
